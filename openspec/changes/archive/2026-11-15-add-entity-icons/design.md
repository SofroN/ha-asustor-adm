# Design

## Context

См. `proposal.md` — Why. Здесь только развилки и их основания.

Наблюдения, важные для решений:

- Зонд по полному набору (`hass.data["entity_components"][domain].entities`) показывает `icon = None` у 40 сущностей интеграции: памяти в процентах, температуры процессора и дисков, ёмкостей тома и внешних дисков, сети, дисковых скоростей, признаков проблем, сущности обновления ADM и кнопок питания.
- Иконка не попадает в атрибуты состояния: `hass.states.get(...).attributes` содержит только `friendly_name`, `unit_of_measurement` и `state_class`. Заданную кодом иконку видно только через саму сущность.
- `SensorEntity.icon` возвращает лишь явно заданное значение; иконку по `device_class` (`data_size` → `mdi:harddisk`, `temperature` → `mdi:thermometer`, `data_rate` → `mdi:speedometer`) подставляет фронтенд, а не бэкенд.
- У `ButtonEntity` нет иконки по умолчанию в коде: фронтенд рисует общий символ нажатия для любой кнопки.
- Имена `mdi` не проверяются ни линтером, ни тестами: неизвестное имя даёт пустой значок без сообщения об ошибке.

## Goals / Non-Goals

**Goals:**

- Один и тот же набор правил: явная иконка только там, где `device_class` не даёт однозначной или не различает смысл.
- Имена иконок гарантированно существуют в версии Home Assistant, против которой идут тесты.
- Правило проверяется тестом, чтобы новая сущность без иконки или случайное дублирование `device_class` были замечены.

**Non-Goals:**

- Замена brand-ассетов интеграции и любые растровые изображения.
- Настройка иконок пользователем (кастомизация в реестре сущностей остаётся штатной возможностью Home Assistant).
- Изменение имён, идентификаторов и доступности сущностей.

## Decisions

### D1. Иконки — `mdi`-имена, а не brand-ассеты

Иконка сущности в Home Assistant — это имя из набора Material Design Icons, которое фронтенд рисует сам; растровые файлы относятся к brand-ассетам интеграции (`brand/icon.png`) и к сущностям не применяются. Поэтому изменение не трогает `brand/` и не требует загрузки графики из сети.

### D2. Явная иконка только там, где `device_class` не даёт однозначной

Правило и его границы:

| Случай | Решение | Пример |
| --- | --- | --- |
| Нет `device_class`, значение — проценты | явная иконка `mdi:memory`, `mdi:chart-donut` | утилизация памяти, тома, внешнего диска |
| Один `device_class` на два разных смысла | явные иконки направления | сеть: `mdi:download-network` / `mdi:upload-network`; диск: `mdi:download` / `mdi:upload` |
| Нет иконки по умолчанию у платформы | явная иконка по действию | кнопки: `mdi:power`, `mdi:restart`, `mdi:power-sleep` |
| `device_class` даёт точную иконку | явную не задаём | `data_size`, `temperature`, `problem`, `update`, `connectivity` |

Дублирование `device_class` отвергнуто: оно добавляет код, который расходится с оформлением Home Assistant при обновлении фронтенда, и ничего не меняет на экране.

### D3. Имена иконок берутся из набора, который использует сам Home Assistant

Проверки имён `mdi` нет ни в линтере, ни в зависимостях: пакет фронтенда с метаданными иконок в окружение тестов не ставится, а сеть в проверках недоступна. Поэтому берутся только имена, которые встречаются в исходниках установленного Home Assistant 2026.10.4 (`mdi:memory`, `mdi:chart-donut`, `mdi:download-network`, `mdi:upload-network`, `mdi:download`, `mdi:upload`, `mdi:power`, `mdi:restart`, `mdi:power-sleep`) — существование в бандле фронтенда гарантировано самой версией, против которой идут тесты.

### D4. Иконка проверяется через сущность, а не через состояние

Иконки нет в атрибутах состояния, поэтому тест берёт объект сущности: `hass.data["entity_components"][domain].get_entity(entity_id).icon`. Альтернатива — проверять `_attr_icon` через реестр — не годится: реестр хранит пользовательский override, а не значение из кода.

### D5. Обратная проверка «не дублируем `device_class`» — часть контракта

Тест утверждает, что у сущностей с точным `device_class` (`cpu_temperature`, `memory_used`, `volume_1_capacity`, `disk_1_temperature`, `external_disk_usb2_capacity`, `adm_update_available`) иконка не задана. Так правило из D2 не размоется при добавлении новых сущностей: явное значение появится только вместе с осознанным решением.
