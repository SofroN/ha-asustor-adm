# Design

## Context

См. `proposal.md` — Why. Здесь только то, что определяет подход.

Проект создаётся с нуля: каталог `ha-asustor-nas` пуст, в `openspec/` есть только этот чейндж. Кода интеграции не существует, поэтому дизайн опирается на результаты спайка, а не на существующую кодовую базу.

Целевое устройство спайка: ASUSTOR AS3304T, ADM `5.1.4.RM62`, AArch64, 2 ГиБ RAM, 4 отсека, два тома (`single`/ext4 7.93 ТБ и `raid1`/ext4 1.96 ТБ), UPS отсутствует, USB-диск подключается периодически.

Ограничения, которые формируют архитектуру:

- Публичной документации на HTTP API ADM не существует; контракт восстановлен по 65 захваченным вызовам и по строкам JS-бандлов. Любое поле может измениться в следующей прошивке.
- ADM по умолчанию отдаёт HTTPS на порту 8001 с самоподписанным сертификатом; требование валидного сертификата исключило бы большинство установок и не прошло бы в HA core.
- Авторизация — единственный путь к данным: без сессии не работает ни один эндпоинт.
- Диски NAS засыпают; опрос — единственный источник данных, поэтому интервалы должны быть настраиваемыми.

## Goals / Non-Goals

**Goals:**

- Один клиент ADM API, переиспользуемый двумя координаторами с общей сессией и единой обработкой ошибок.
- Разложение сущностей по возможностям устройства, чтобы на других моделях не появлялись датчики без данных.
- Устойчивый разбор ответов: отсутствие поля ухудшает одну сущность, а не весь цикл опроса.
- Секреты и идентификаторы сессии не попадают в журналы и в диагностику.
- Тесты без реального NAS: разбор и поведение координаторов проверяются на сохранённых ответах.

**Non-Goals:**

- Использование long-polling `events.cgi` для событий в реальном времени — в этой итерации опрос по таймеру, событийная модель отложена.
- Сущности по шарам (`activityMonitor/disk.cgi`) и по процессам (`activityMonitor/process.cgi`) — слишком много сущностей для первой версии.
- Сбор и хранение журналов ADM, регистрационных данных учётной записи ASUSTOR (`register.cgi`).
- Поддержка нескольких NAS в одной записи: одна запись — один NAS.
- Публикация метрик в стиле `/metrics`; интеграция только публикует сущности HA.

## Decisions

### D1. Транспорт: HTTP API ADM, а не SNMP

Три существующих сторонних проекта уже используют SNMP, и SNMP физически не может выключать NAS, показывать статусы сервисов и доступность обновления ADM. Выбор HTTP API даёт дифференциацию, которую невозможно воспроизвести через SNMP.

Альтернативы: SNMP-интеграция (отклонено — четвёртый дубль без новых возможностей), гибрид SNMP+HTTP (отложено как расширение: у HTTP API уже есть мониторинг, SNMP добавлял бы только независимый путь к тем же данным).

Следствие: зависимость от непубличного контракта принимается осознанно и компенсируется tolerant-разбором (D4, D9).

### D2. Имена: репозиторий `ha-asustor-adm`, домен `asustor_adm`

Дефис в имени домена HA невозможен — домен это имя каталога и Python-идентификатор. Домен `asustor` уже занят сторонним HACS-проектом, `asustor_snmp` — другим; конфликт доменов при совместной установке недопустим.

### D3. Клиент: `aiohttp`, обязательное пустое тело, `sid` в query

Запросы — `POST /portal/apis/<module>/<name>.cgi?sid=<sid>&act=<verb>` с `Content-Type: application/x-www-form-urlencoded`.

Ключевые требования, установленные на практике:

- Пустое тело передаётся **явно** (`data=b""`). Без `Content-Length` сервер отвечает `411 Length Required` — проверено на реальном запросе.
- Параметр `_dc` (cache-buster интерфейса) не обязателен — проверено запросом без него.
- Кука сессии не используется: `sid` передаётся параметром. Cookie-jar отключается, чтобы не тащить состояние между записями.
- Проверка TLS — параметр записи. По умолчанию включена; выключение доступно, но требует явного действия пользователя и описано в документации.
- Тайм-аут: 10 с на запрос, отдельный более короткий тайм-аут на авторизацию, чтобы настройка не «висела».

### D4. Конверт ошибок и типизация сбоев

Наблюдаемые формы ответов различаются, и опираться на одно поле нельзя:

| Форма ответа | Трактовка |
|---|---|
| `{"success": true, ...}` | успех |
| `{"success": false, "error_code": 5000}` | сессия недействительна → одна повторная авторизация и один повтор запроса |
| `{"success": false, "error_code": 6300, "error_msg": "..."}` | прикладная ошибка устройства → сущность недоступна, повтора нет |
| `{"error_code": 6209}` / `{"error_code": 6215}` / `{"error_code": 5005}` — без `success` | неуспех: код означает «проверка недоступна/нет данных», не сбой связи |

Правило: успех — только при явном `success is True`. Отсутствие `success` при наличии `error_code` — неуспех. Код `5000` — единственный, приводящий к повторной авторизации; остальные коды не ретраятся.

Альтернатива — считать любой неразобранный ответ сбоем связи — отклонена: она превращала бы «нет обновлений» в недоступность всех сущностей.

### D5. Два координатора с общим клиентом

- Быстрый (по умолчанию 60 с): `activityMonitor/act.cgi?act=list`, `information/sysinfo.cgi?act=sys`, `storageManager/volume.cgi?act=list`, `storageManager/disk_smart.cgi?act=list` — 4 запроса.
- Медленный (по умолчанию 300 с): 8 эндпоинтов сервисов (`SERVICE_ENDPOINTS`: SSH и SFTP приходят из одного `services/terminal.cgi`, AFP через `services/mac.cgi` не опрашивается — сущности для него нет), `information/sysinfo.cgi?act=net`, `information/sysinfo.cgi?act=wan`, `information/onlineuser.cgi?act=list`, `external/extdisk.cgi?act=list`, `taskmonitor/taskmonitor.cgi?act=task_list`, `settings/firmwarestatus.cgi?act=get_static_info`, `appCentral/appcentral.cgi?act=count` — 15 запросов плюс по одному `storageManager/volume.cgi?act=get&vid=N` на каждый том, итого 17 на AS3304T с двумя томами.

По запросу, вне циклов: только `disk_smart.cgi?act=smart&did=N` — атрибуты SMART запрашиваются сущностью, отключённой по умолчанию. `volume.cgi?act=get` перенесён в медленный цикл: сведения RAID (`member`, `spare`, `failed`, `removed`) есть только в нём, а спецификация `storage-health` требует публиковать их как атрибуты тома.

Два координатора, а не один, потому что смешивание редких данных с частыми вынудило бы либо опрашивать все эндпоинты медленного цикла каждую минуту, либо обновлять загрузку CPU раз в пять минут. Каждый координатор имеет свой `UpdateInterval` и общий `ADMClient`.

Отдельно решено **не использовать** `activityMonitor/act.cgi?act=get`: он возвращает только суммарные проценты, которые вычисляются из данных `act=list`. И не использовать `disk.cgi?act=list`: `disk_smart.cgi?act=list` отдаёт надмножество полей, включая `smart_status`.

### D6. Единицы измерения и вычисляемые значения

- Память: `memtotal`/`memused`/`memcached`/`membuffer` — в килобайтах (`memtotal: 1983612` против `mem: 2048` МиБ из `sysinfo`). В сущности переводится в МиБ, доля считается как `memused / memtotal`.
- Объёмы томов и дисков — в байтах, приводятся к ГиБ.
- Сеть: единица `kB/s` и семантика полей подтверждены двумя контрольными замерами. При передаче данных на NAS: `rx = 21522–22738`, `tx = 214–226`; при чтении с NAS: `tx = 14498–21541`, `rx = 54–95`. Значит `rx` — приём NAS, `tx` — передача NAS; 21500 кБ/с ≈ 21 МБ/с ≈ 172 Мбит/с, что соответствует гигабитному каналу. Обе сущности публикуются включёнными, с `device_class: data_rate` и `state_class: measurement`.
- Дисковый ввод-вывод: `kB/s`, объекты публикуются по каждому диску. При записи на NAS `write` достигал 22155–27599 при `rx = 21522–22738`; при чтении с NAS `read` достигал 14375–21500 при `tx = 14498–21541`. Показатель чтения зависит от кэша страниц (1 ГиБ из 1.9 ГиБ): при обслуживании из кэша `read` остаётся нулевым, что не является неисправностью.
- Числовые значения приходят строками, иногда с завершающим переводом строки (`"2.22\n"`) — обязателен `strip()` перед приведением к числу.

### D7. Гейтирование по возможностям устройства

В ответе авторизации ADM сообщает флаги: `isadministrators`, `canwol`, `cansuspend`, `haslcm`, `canhotplug`, `chassis`, `bays`, `haslaststate`. Правила:

| Флаг/данные | Что включают |
|---|---|
| `isadministrators` | кнопки выключения и перезагрузки |
| `cansuspend` | кнопка сна (на AS3304T — `false`) |
| длина `fan_speed[]` | число сущностей кулеров |
| `bay` из `volume.cgi?act=list` | ожидаемое число дисков |
| наличие `disks[]` в `extdisk.cgi` | сущности внешних дисков |

### D8. Идентификаторы и стабильность сущностей

`unique_id` строится из серийного номера NAS и стабильного ключа объекта: для дисков — номер отсека, для томов — `vid`, для сервисов — имя сервиса. Серийный номер берётся из `sysinfo.cgi?act=sys`, при его отсутствии — из адреса хоста. Номер отсека предпочтён `did`/имени устройства (`sdc`), потому что нумерация `sdX` меняется между загрузками.

### D9. Ухудшение вместо отказа

Разбор ответов выполняется функцией, возвращающей результат по каждому полю отдельно. Отсутствующее поле делает недоступной только связанную сущность; исключение внутри разбора не должно прерывать координатор. Неизвестные лишние поля игнорируются.

### D10. Поведение при недоступности и после команд питания

Ошибка соединения переводит координатор в состояние сбоя (сущности недоступны), но не создаёт новых попыток входа. После успешной команды `admin.cgi?act=shutdown|restart` координаторы помечаются недоступными намеренно, чтобы не заваливать NAS запросами во время выключения; восстановление происходит само при первом успешном ответе.

Отдельная логика распознавания внешнего выключения не вводится: недоступность устройства одинаково отражает и выключение из HA, и выключение кнопкой.

### D11. Маскирование секретов

`diagnostics.py` заменяет `password`, `sid`, `passport`, `account`, серийный номер и IP-адреса; из URL удаляется query string (там `sid`). Тело запроса авторизации не попадает в диагностику никогда. В журналах используется только путь эндпоинта.

### D12. Тестирование без NAS

Тесты строятся на сохранённых ответах спайка (очищенные фикстуры тех же форм) и на подменённом HTTP-транспорте:

- разбор: наличие/отсутствие полей, строки с переводом строки, форматы SMART;
- конверт ошибок: `5000` → одна повторная авторизация, прочие коды → без ретрая;
- гейтирование: администратор/не администратор, `cansuspend` true/false;
- уникальность `unique_id`, стабильность при повторной настройке.

Живой NAS в CI не участвует.

### D13. Состав сущностей

70 сущностей на AS3304T с двумя подключёнными внешними дисками:

- 48 сенсоров: 12 статических (загрузка CPU, 3 нагрузки, память в МиБ и в процентах, uptime, IP-адрес, внешний IP, сессии, обновления App Central, активные задачи) и 36 динамических (4 ядра, температура, 1 кулер, 2 направления обмена для интерфейса, 2 тома × 3, 4 диска × (температура + чтение + запись + SMART), 2 внешних диска × 3);
- 20 двоичных признаков: 9 сервисов, 2 тома, 4 диска, доступность обновления ADM, наличие и готовность двух внешних дисков;
- 2 кнопки: выключение и перезагрузка (`cansuspend: false`, кнопка сна не создаётся).

6 сущностей отключены по умолчанию: 4 сущности SMART, «Активные задачи» и внешний IP (диагностический). Сущность обновления ADM не создаётся, пока целевая версия неизвестна; версия ADM публикуется как сведение об устройстве.

## Risks / Trade-offs

- **Непубличный контракт API изменится в прошивке** → tolerant-разбор (D9), диагностика содержит версию ADM, набор фикстур пополняется при поломках; отсутствие поля ухудшает одну сущность, а не всю интеграцию.
- **Пароль администратора NAS хранится в записи интеграции** → это неизбежно: `sid` живёт 60 минут (`timeout_minutes: 60`), и без пароля восстановление сессии невозможно. Митигация: рекомендация отдельной учётной записи, предупреждение в документации, маскирование в диагностике.
- **Блокировка адреса после неудачных попыток входа** → не более одной повторной авторизации на запрос, экспоненциальная пауза между циклами при сбоях авторизации, отсутствие ретраев внутри цикла.
- **Двухфакторная авторизация не проверена** → параметр `two-step-auth` в API есть, но на тестовом аккаунте 2FA выключена. Митигация: явная ошибка при настройке вместо тихого сбоя; поддержка добавляется после получения формы ответа от пользователя с включённой 2FA.
- **Направления сетевых счётчиков и семантика дискового ввода-вывода** подтверждены двумя контрольными замерами (передача файла на NAS: `rx ≈ 21500`, `write ≈ 22000`; чтение с NAS: `tx ≈ 15000–21500`, `read ≈ 14000–21500` кБ/с). Сущности включены по умолчанию, у всех скоростных сенсоров заданы `device_class: data_rate` и `state_class: measurement`.
- **Page cache маскирует чтение с диска** → нулевое `read` при активной передаче с NAS не является неисправностью (1 ГиБ кэша из 1.9 ГиБ); поведение описано в README, `state_class: measurement` при этом сохраняется, чтобы нулевые значения не выпадали из статистики.
- **Медленный цикл — 17 запросов на слабом AArch64** (два тома): каждый запрос порождает CGI-процесс в ADM. Интервал по умолчанию 300 с, при жалобах на нагрузку увеличивается пользователем в настройках записи.
- **Внешний IP отсутствует без доступа к интернету** → сенсор отключён по умолчанию и не влияет на остальные сущности; при пустом `wanip` он остаётся недоступным.
- **Опрос мешает засыпанию дисков** → интервалы настраиваемые, дефолт 60/300 с; при жалобах на недосыпание рекомендуется увеличить оба.
- **ADM 4.x не проверялась** → версия публикуется в сведениях об устройстве, чтобы отчёты об ошибках содержали контекст; кодовые пути не привязаны к 5.x, кроме отсутствующих полей, которые обрабатываются как обычно.
- **Модель без второго кулера/без датчика температуры** → гейтирование по длине массивов в ответе.
- **Опрос создаёт нагрузку на CGI-процессы ADM** (каждый запрос — процесс) → 4 запроса в минуту на слабом AArch64-устройстве приемлемо, медленный цикл вынесен отдельно; при необходимости интервалы увеличиваются пользователем.
- **Проверено только на одной модели** (AS3304T, 4 отсека, 2 тома) → набор фикстур для одного устройства; расширение на другие модели требует новых дампов, поэтому сведения о модели и версии всегда доступны в устройстве.

## Migration Plan

Зелёное поле: миграции нет, существующие данные отсутствуют.

1. Выпуск `0.1.0` как HACS custom repository (`ha-asustor-adm`), установка через HACS → перезапуск HA → добавление записи.
2. Откат: удаление записи интеграции, затем удаление репозитория из HACS. Данные на NAS не затрагиваются — интеграция не меняет настройки устройства, кроме команд питания, отправляемых только по явному действию.
3. После первого релиза набор фикстур пополняется реальными ответами при сообщениях о поломках на других моделях.

## Open Questions

- Форма ответа ADM при включённой 2FA: нужен дамп от пользователя с двухфакторной авторизацией.
- Точный смысл кодов `6209`, `6215`, `5005`: сейчас трактуются как «проверка недоступна»; уточняется по мере накопления отчётов.
