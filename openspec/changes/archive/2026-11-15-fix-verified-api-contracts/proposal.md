# Proposal

## Why

Контракт API ADM восстановлен по захватам на одном устройстве, и часть его осталась непроверенной. Проверка на официальном демо-портале ASUSTOR (`asrdemo.myasustor.com`, AS7110T, ADM 5.1.4.DM62, учётная запись администратора) показала три расхождения кода с фактическим поведением устройства; на живом NAS они дают постоянно недоступные сущности и неверную причину отказа настройки.

1. **Запросы состояния пяти служб уходят без параметра `tab`.** Интерфейс ADM запрашивает их как `windows.cgi?act=get&tab=cifs`, `nfs.cgi?act=get&tab=Nfs_Get_Enable`, `ftp.cgi?act=get&tab=general`, `http.cgi?act=get&tab=webdav`, `snmp.cgi?act=get&tab=Get`. Без `tab` устройство отвечает `{"success": false, "error_code": 5302}` (у `http.cgi` — `5303`) с текстом `error_msg: "tab"` и полей `enable` / `IsEnabled` / `webdav_enable` / `enable_snmp` не возвращает. Значит, признаки SMB, NFS, FTP, WebDAV и SNMP на реальном устройстве недоступны всегда, а фикстуры этих служб получены из запросов интерфейса (с `tab`) и потому расхождения не показывали. SSH, SFTP, rsync и TFTP отвечают без `tab` — у них расхождения нет.
2. **Список сессий запрашивается без параметров постраничности.** `onlineuser.cgi?act=list` отвечает `5302`, а `act=list&sort=0&ascend=0&start=0&limit=20` — `{"success": true, "total": N, "datas": [...]}`. Число активных сессий на реальном устройстве недоступно всегда.
3. **Двухфакторная авторизация распознаётся по несуществующей форме ответа.** Клиент искал в ответе авторизации поля с именами `two-step*` / `otp` / `verify`. Фактический контракт (код интерфейса ADM 5.1.4): запрос авторизации несёт `two-step-auth`, при включённой 2FA устройство отвечает `{"success": false, "error_code": 5034}` (`TWO_STEP_CHECK`), повторный запрос добавляет `verifycode` с шестизначным кодом, неверный код даёт `6200` (`TWO_STEP_ERROR`). Из-за неверного признака пользователь с 2FA получает «неверные учётные данные» вместо «требуется одноразовый код».

Дополнительно закрыты открытые вопросы `design.md`:

- смысл кодов проверки обновлений: по карте ошибок самого интерфейса ADM `6209` — «установлена последняя версия», `6215` — «та же версия», `5005` / `5601` / `5814` — нет связи с сервером обновлений, `5608` — тайм-аут соединения, `5303` — неверный параметр, `5026` — система только для чтения. Прежние имена констант (`5005` — «нет локальных данных», `6209` — «проверка невозможна») неверны;
- коды контекстны для каждого CGI: `5005` у `volume.cgi` значит «нет такого тома», у `firmwarestatus.cgi` — «нет связи с сервером обновлений», поэтому общий набор кодов не должен трактоваться вне эндпоинта;
- активная проверка обновлений имеет подтверждённый контракт: `GET firmwarestatus.cgi?act=get_new_adm_info_from_remote_server&timeout=60&distinguish_same_from_up_to_date=true&lang=<локаль>` возвращает `version`, `link`, `release_date`, `release_note_link`; `act=get_updating_status` возвращает `{"phase": 0, "success": true}`. Реализация такой проверки — отдельное изменение, здесь контракт только фиксируется;
- `admin.cgi` не проверяет действие: `act=bogus` возвращает `{"success": true}`, поэтому ошибку команды питания конвертом не обнаружить.

## What Changes

- Эндпоинт получает параметры контракта, которые клиент передаёт в query каждого запроса: `tab` для SMB/CIFS, NFS, FTP, WebDAV и SNMP, параметры постраничности для списка сессий. Состав служб, их поля и число запросов цикла не меняются.
- Авторизация передаёт признак `two-step-auth` и распознаёт требование одноразового кода по коду `5034`; поведение при отказе не меняется — настройка завершается отдельной причиной «требуется двухфакторная авторизация».
- Константы кодов проверки обновлений переименованы по подтверждённым значениям, а комментарий фиксирует контекстность кодов.
- Тесты: параметры контракта в `const.py` и в query запроса, признак `two-step-auth` в форме авторизации, распознавание `5034`; фикстура `login_two_factor` приведена к фактической форме ответа.

Не делаем:

- активную проверку обновлений через `get_new_adm_info_from_remote_server`: это новый запрос в цикле и отдельное решение о периодичности, нужен самостоятельный чендж с учётом того, что `5.1.4.DM62` против `5.1.4.RM62` — разные сборки одной версии;
- поддержку ввода одноразового кода в потоке настройки: остаётся явная ошибка, как решено ранее;
- замену общего набора кодов на разбор по эндпоинту: пока коды обновлений ни в одном решении не участвуют, достаточно корректных имён и комментария;
- сущность системной температуры (`systemp`), которая есть у AS7110T, но отсутствует у AS3304T.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `services-status`: требования «Статусы сетевых сервисов» и «Число активных сессий» дополняются обязательными параметрами запроса, без которых ADM сведений не отдаёт.
- `system-metrics`: требование «Настройка подключения» дополняется сценарием учётной записи с двухфакторной авторизацией.

## Impact

- `custom_components/asustor_adm/const.py` — `Endpoint.params`, параметры `tab` и постраничности, имена кодов обновлений и код `5034`;
- `custom_components/asustor_adm/api.py` — параметры эндпоинта в query, признак `two-step-auth`, распознавание `5034` вместо перебора имён полей;
- `tests/conftest.py`, `tests/unit/test_const.py`, `tests/unit/test_api.py`, `tests/fixtures/login_two_factor.json`, `tests/fixtures/README.md` — проверки и происхождение фикстуры;
- `CHANGELOG.md` — раздел «Исправлено»; `README.md` — число тестов.
