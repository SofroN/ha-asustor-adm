# Design

## Context

См. `proposal.md` — Why. Здесь только то, что определяет подход.

Источник фактов — живой демо-портал ASUSTOR (`asrdemo.myasustor.com:8481`, AS7110T, ADM 5.1.4.DM62) и код интерфейса ADM версии 5.1.4, который портал отдаёт открыто: `cores/main.js` (авторизация, двухфакторный режим), `apps/settings/functions/maintenance.js` (проверка обновлений и карта кодов), `apps/services/functions/*.js` (запросы состояния служб), `apps/systemInformation/functions/online.js` (список сессий). Код интерфейса — такой же первоисточник контракта, как захват запроса: запросы интерфейса и есть те запросы, которые обязана повторять интеграция.

Демо-портал отличается от целевого устройства: другая модель (10 отсеков, 4 сетевых порта, два кулера, `cansuspend: true`), сборка `5.1.4.DM62` вместо `5.1.4.RM62` и удалённая сессия (`isfromlocal: false`). Поэтому проверялись формы ответов и обязательность параметров, а не значения метрик.

## Goals / Non-Goals

**Goals:**

- Привести запросы интеграции в соответствие с контрактом, который использует интерфейс ADM, и получить на живом устройстве те же поля, что в фикстурах.
- Дать пользователю с включённой 2FA правильную причину отказа.
- Зафиксировать подтверждённые значения кодов, чтобы следующее изменение опиралось на факты.

**Non-Goals:**

- Новые эндпоинты и новые сущности: состав запросов остаётся прежним.
- Поддержка ввода одноразового кода и активная проверка обновлений.

## Decisions

### D1. Параметры контракта — часть описания эндпоинта

`Endpoint` получает поле `params: tuple[tuple[str, str], ...]`, а `ADMClient._async_send` добавляет их в query после `act`. Так требование контракта живёт рядом с путём и действием, попадает в каждый запрос и не требует ни менять координаторы, ни передавать параметры в каждом вызове.

Значения параметров берутся из запросов интерфейса ADM дословно:

| Служба | Запрос интерфейса | Поле ответа |
|---|---|---|
| SMB/CIFS | `services/windows.cgi?act=get&tab=cifs` | `enable` |
| NFS | `services/nfs.cgi?act=get&tab=Nfs_Get_Enable` | `IsEnabled` |
| FTP | `services/ftp.cgi?act=get&tab=general` | `enable` |
| WebDAV | `services/http.cgi?act=get&tab=webdav` | `webdav_enable` |
| SNMP | `services/snmp.cgi?act=get&tab=Get` | `enable_snmp` |
| SSH, SFTP | `services/terminal.cgi?act=get` | `ssh_enable`, `sftp_enable` |
| rsync | `services/rsync.cgi?act=get_sets` | `rsync_enable` |
| TFTP | `services/tftp_server.cgi?act=get` | `enabled` |

Альтернативы: передавать `tab` из координатора — разбрасывает контракт по вызовам и ломает ключ кэша `SERVICE_ENDPOINTS`; добавлять поле в `ServiceDefinition` — потребовало бы группировать запросы по паре «эндпоинт + параметры» вместо готового `SERVICE_ENDPOINTS`. Обе отклонены как усложнение без выгоды.

Уникальность `SERVICE_ENDPOINTS` сохраняется: SSH и SFTP по-прежнему делят один `terminal.cgi` без параметров, остальные различаются путём.

### D2. Постраничность списка сессий обязательна

`onlineuser.cgi?act=list` без параметров отвечает `5302`; работают только `sort`, `ascend`, `start` и `limit` вместе (проверены наборы из одного, двух и трёх параметров — все отклонены). Берётся тот же набор, что у интерфейса: `sort=0&ascend=0&start=0`, `limit=100`. Значения `limit` 20, 100 и 1000 дают одинаковый `total`, поэтому `limit` влияет лишь на размер страницы `datas`, а число сессий читается из `total`, как и раньше.

### D3. Двухфакторная авторизация распознаётся по коду ответа

Клиент передаёт `two-step-auth=true` в форме авторизации — так делает интерфейс ADM и при выключенной 2FA (параметр игнорируется), и при включённой. Требование кода распознаётся по `error_code: 5034`, отказ по неверному коду — `6200`. Перебор имён полей ответа убран: таких полей устройство не присылает, и признак не срабатывал никогда.

Альтернативы: оставить перебор имён как страховку — он маскирует ошибку и не подтверждён ни одним ответом; считать признаком любой неуспешный ответ — смешало бы 2FA с неверным паролем. Обе отклонены.

Ввод одноразового кода не реализуется: поток настройки по-прежнему завершается ошибкой `two_factor`, но теперь по правильной причине.

### D4. Коды проверки обновлений: подтверждённые значения и границы применимости

Карта ошибок интерфейса ADM (`apps/settings/functions/maintenance.js`, объект `ERROR_CODE_MAP_TABLE`):

| Код | Значение | Как показано в интерфейсе |
|---|---|---|
| `5005` | нет связи с сервером обновлений | «не удаётся подключиться» |
| `5601`, `5814` | нет связи с сервером обновлений | «не удаётся подключиться» |
| `5608` | тайм-аут соединения | ошибка соединения |
| `5026` | система только для чтения | — |
| `5303` | неверный параметр | — |
| `6209` | установлена последняя версия | зелёный текст «последняя версия» |
| `6215` | предлагаемая версия совпадает с установленной | «та же версия» |

Отсюда: константы `5005` и `6209` переименованы по смыслу, набор «новее нет» состоит из `6209` и `6215`, а `5005` означает сбой проверки, а не «нет данных». Дополнительно зафиксировано, что коды контекстны: `volume.cgi?act=get` с несуществующим `vid` отвечает `5005 "No such volume"`, поэтому общий набор кодов нельзя трактовать вне эндпоинта, и в комментарии это сказано.

Значения не влияют на поведение до появления активной проверки: сейчас коды обновлений ни в одном решении не участвуют.

### D5. Активная проверка обновлений — отдельное изменение

Контракт подтверждён: `firmwarestatus.cgi?act=get_new_adm_info_from_remote_server` с `timeout`, `distinguish_same_from_up_to_date` и `lang` возвращает `version`, `link`, `release_date`, `release_note_link`; на демо-устройстве это `5.1.4.RM62` при установленной `5.1.4.DM62`. Это ровно тот случай, где сравнение версий по сегментам даёт «обновление доступно» для другой сборки той же версии. Реализация требует решения о периодичности, о поведении при отсутствии интернета на NAS и о различении сборок (`DM`/`RM`), поэтому выносится в отдельный чендж; здесь фиксируется только контракт.

## Risks / Trade-offs

- [Параметр `tab` может быть необязательным на других прошивках] → интерфейс ADM 5.1.4 передаёт его всегда, лишний параметр устройство игнорирует; на ADM 4.x проверки нет, но и прежний вариант там не подтверждён.
- [Коды `5302`/`5303` могут означать не только отсутствие параметра] → трактовка не меняется: неуспешный ответ делает сущность недоступной, повтора нет; в журнал по-прежнему пишется только путь и код.
- [Демо-устройство отличается от целевого] → проверялись формы и обязательность параметров; значения метрик и состав сущностей на AS3304T не перепроверялись.
- [Передача `two-step-auth=true` на прошивках без 2FA] → параметр игнорируется, что подтверждено входом на демо-устройстве с выключенной 2FA; при включённой он и нужен, чтобы получить `5034`.
- [Фикстура `login_two_factor` синтетическая] → её форма взята из кода интерфейса ADM, живой захват недоступен: на тестовых учётных записях 2FA выключена. Это указано в `tests/fixtures/README.md`.

## Migration Plan

Поведение сущностей меняется только в сторону доступности: ранее недоступные признаки служб и число сессий начинают публиковать значения. Записей и сущностей это не касается, миграции нет; откат — возврат параметров эндпоинтов и проверки 2FA.

## Open Questions

- Поведение запросов состояния служб на ADM 4.x не проверено: нужен захват интерфейса на устройстве с ADM 4.
- Точная причина отказов `5302`/`5303` на устройстве без `tab` остаётся реконструкцией по тексту `error_msg: "tab"`; отдельного кода «недостаточно прав» для служб не наблюдалось.
